


1. Create the GKE cluster
gcloud container clusters create moodle-gke-cluster \
  --zone northamerica-northeast2-a \
  --num-nodes 2 \
  --machine-type e2-medium
2. Connect kubectl to GKE
gcloud container clusters get-credentials moodle-gke-cluster \
  --zone northamerica-northeast2-a

Verify:

kubectl get nodes

3. Deploy 01–04

01 Storage
relaxes Kustomize's file-loading security restriction:
kubectl kustomize --load-restrictor LoadRestrictionsNone kubernetes/gcp-gke/storage/
kubectl kustomize --load-restrictor LoadRestrictionsNone \
  kubernetes/gcp-gke/storage/ | kubectl apply -f -

kubectl get pvc

02 MySQL
kubectl kustomize --load-restrictor LoadRestrictionsNone kubernetes/gcp-gke/mysql/
kubectl kustomize --load-restrictor LoadRestrictionsNone \
  kubernetes/gcp-gke/mysql/ | kubectl apply -f -
kubectl get pods -w

03 PHP
kubectl kustomize --load-restrictor LoadRestrictionsNone kubernetes/gcp-gke/php/
kubectl kustomize --load-restrictor LoadRestrictionsNone \
  kubernetes/gcp-gke/php/ | kubectl apply -f -

Verify the PHP image:

kubectl get deployment php \

 NOTE: GCP falls back to checking / on port 80. Since Moodle catches / and issues a 302 Redirect to /login/index.php (or similar), the load balancer marks the backend as unhealthy.
 
Check GKE load balancer was created correctly first.
GKE reports the nginx backend as HEALTHY or UNHEALTHY.
kubectl describe ingress moodle-ingress

expected
nginx:80 → UNHEALTHY

gcloud compute health-checks list

gcloud compute health-checks describe \

HTTP
port = serving port (80)

Good. Now we know exactly what GKE is checking:

HTTP
port = serving port (80)
path = /
timeout = 15s

So GKE is effectively doing:

GET http://10.100.0.7:80/

and deciding it is unhealthy.

kubectl exec -it nginx-747ccd6c85-8tw6b -- curl -I http://10.100.0.7/

expected:

note A missing readiness probe is not automatically the cause of the GKE health check failure.
